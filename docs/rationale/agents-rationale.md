# AGENTS.md 작성 이유와 예시

이 문서는 `AGENTS.md`의 주요 규칙을 왜 이렇게 작성했는지 설명한다. 실제 작업 규칙은 루트의 `AGENTS.md`를 기준으로 한다.

# 작업별 필수 문서

## 왜 필요한가

Codex가 모든 문서를 매번 읽으면 맥락 비용이 커진다. 반대로 아무 문서도 읽지 않으면 API, DB, 아키텍처 규칙을 놓치기 쉽다. 그래서 자주 필요한 규칙은 하나의 공통 문서로 모았다.

## 예시

- Controller, Entity 또는 Flyway를 바꿀 때는 `docs/conventions.md`를 먼저 읽는다.
- API를 추가하거나 변경할 때는 `docs/api.md`의 구현 상태도 함께 갱신한다.

# Superpowers 작업 흐름

## 왜 필요한가

새 기능이나 인증·인가처럼 설계 선택지가 많은 작업은 바로 구현하면 되돌릴 가능성이 높다. 반면 테스트 케이스 하나 추가나 문서 정리는 큰 설계가 필요하지 않다. 그래서 Superpowers는 모든 작업에 강제하지 않고, 위험도가 있거나 설계가 필요한 작업에 우선 적용하도록 했다.

## 예시

- `POST /api/products` Controller를 새로 만들면 인증 방식, 요청 DTO, 응답 DTO, 예외 응답을 정해야 하므로 먼저 범위를 정리한다.
- `ProductTest`에 가격 검증 케이스를 하나 추가하는 작업은 기존 정책을 확인하고 바로 보강해도 된다.

# 승인과 실행

## 왜 필요한가

DB 스키마, 공개 API, 인증 정책은 한 번 바꾸면 이후 코드와 문서, 테스트가 연쇄적으로 바뀐다. 이런 변경은 사용자 승인 후 진행하는 편이 안전하다. 반대로 작은 문서 수정이나 테스트 보강까지 매번 승인을 받으면 학습과 개발 흐름이 느려진다.

## 예시

- `products` 테이블에 `thumbnail_url` 컬럼을 추가하는 작업은 Flyway, Entity, API 응답이 함께 바뀔 수 있으므로 사전 승인을 받는다.
- README의 실행 명령을 고치는 작업은 공개 API나 DB에 영향을 주지 않으므로 작업 범위를 알리고 바로 수정할 수 있다.

# 검증 기준

## 왜 필요한가

테스트를 실행하지 않았는데 통과했다고 말하면 프로젝트 상태를 잘못 판단하게 된다. 특히 Spring Boot 프로젝트는 테스트 프로필은 통과하지만 기본 프로필 기동은 실패할 수 있다.

## 예시

- Service 로직만 바꿨다면 관련 Service 테스트를 먼저 실행하고, 이후 전체 테스트를 실행한다.
- Flyway나 Entity를 바꿨다면 `./gradlew test`뿐 아니라 기본 프로필 애플리케이션 기동도 확인한다.
